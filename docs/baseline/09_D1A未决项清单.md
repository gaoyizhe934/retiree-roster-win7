## 1. GATE0_BLOCKER

### A-D1-01 是否还有第二份独立业务工作簿

- **为什么必须在 Gate 0 决定**：Gate 0 即数据边界冻结，而台账 D1-A 要求盘点两份 Excel。字段字典的“完整性”在缺少一份可能存在的业务源时无法被审查；若 D2 冻结契约后才发现第二个来源带有业务必需字段，只能改契约并迁移数据库。
- **本项只回答业务文件数量**：答案为“存在／不存在”。**不得**由“只有一个工作簿”推导“区域 1 不是导入源”，也不得由本项推导任何表头体系的地位——表头体系的性质由 A-D1-07 独立决定。
- **已经验证**：仓库受控文件已枚举；项目目录 `D:\retiree-roster`（含 `tools\`，排除 `.git`）全量扫描 `*.xlsx`／`*.xls`／`*.xlsm`，只有业务样表 `reference/员工信息表11111.xlsx` 与项目管理台账 `reference/七阶段开发任务清单.xlsx`（四个工作表均为管理台账，不是业务数据源）。业务样表的指纹、工作表名、维度与两套表头行均已机器校验。
- **仍可继续的工作**：字段字典、两套表头的逐列映射、重复候选规则、L0 盘点证据均已完成，不依赖本项答案。
- **最小人类问题**：除现有业务样表外，首期是否还有第二份独立业务 Excel？见[审查包](../status/GATE0_A_REVIEW_PACKET.md)决策表 Q1（A 存在／B 不存在）。
- **A 轨不代选**：按指令，A 轨不对 A／B 作推荐；只登记两选项的影响范围。

### A-D1-07 当前 Sheet1 的两套表头体系分别是什么性质

- **为什么必须在 Gate 0 决定**：同一工作表的行 1（52 个非空标题）与行 3（23 个非空标题）是两套明显不同的字段体系，行 1 内部还分成业务维护段、姓名一致性标记列、人事对照段与待遇／考核段，且两区域有 12 个完全同名标题、6 组区域 1 内部精确重复标题。在两套体系的地位未确认前，**源字段映射边界没有真正冻结**：不能断言哪一套是首期导入源，也不能断言另一套是历史结构。
- **已经验证**：两套表头的列集合、规范化键、重复键、跨区域同名键、合并单元格与受保护区域均已逐字节盘点并机器校验（见 [L0 证据](../evidence/D1-A/01-source-header-inventory.txt)）；行 1 的 52 列已全部给出候选处置（20 `PersonField`／27 `BatchRawOnly`／5 `Unsupported`），行 3 的 23 列沿用既有候选映射；数据行为 0。
- **最小人类问题**：两套表头体系是什么关系？四选一，见[审查包](../status/GATE0_A_REVIEW_PACKET.md)决策表 Q2（A 两套都是首期需要支持的 Source Profile／B 行 1 有效，行 3 为历史或辅助结构／C 行 3 有效，行 1 为历史或辅助结构／D 其他，由甲方说明）。
- **推荐默认方案**：**A**（两套都作为首期需要支持的候选 Source Profile）。理由：两套结构都有实际业务列（行 1 有人员状态、类别、社保卡手机号、特困年度等，行 3 有学历、学位、入党时间、籍贯等），在无业务证据时宣告任一套为“历史结构”会丢源；A 对“实际维护哪一套”这一未知不做假设。代价见下。
- **采用默认方案的影响**：A → 需要两个 Profile；行 1 逐列映射细节（哪个电话列映射 `Phone`、`现居地` 是否等同 `HomeAddress`、业务段与人事段谁权威）须在 D3 逐项确认，且行 1 的 5 个 `Unsupported` 列按现行策略阻断确认，需要维护员逐批处置；B → 行 1 封存为非导入结构，其人员状态、类别、特困等列失去导入路径，只能人工录入，且 `LifeStatus`／`PersonnelCategory` 在首期无导入来源；C → 行 3 封存，需为行 1 新建完整 Profile 并重评 8 个无同名键可比对的目标；D → 由甲方说明后重新评估映射表与 Profile 候选。
- **回答之后转入 D3 的细节**（不另占 Gate 0 决策）：`现居地` 与 `HomeAddress` 是否等同；五个以上电话来源中哪一列映射 `Phone`；业务维护段与人事对照段在重复列上的权威顺序。

## 2. REGISTERED_MAPPING_RULE（已登记口径，不阻塞）

### A-D1-06 工号与固定编号：四个标识符概念

上层需求（R05）只冻结三件事：固定人员编号 **≠** 当次打印序号；固定编号稳定；当次序号随筛选结果生成。据此**不再默认**“若工号等同固定编号则删除 canonical `person_code`”，改为登记以下稳定模型：

| 概念 | 契约成员 | 性质 |
| --- | --- | --- |
| 内部主键 | `person_id`（Identifier） | 系统生成、不复用；`source_importable=false`、`user_editable=false`、`system_managed=true`、不打印 |
| 源工号 | `employee_no`（Text） | 来自源表的两套“工号”列；可导入、可人工编辑、可打印，可空可重复 |
| 固定业务编号 | `person_code`（Identifier） | `source_importable=false`、`user_editable=false`、`system_managed=true`、可打印；**只能由服务分配** |
| 当次序号 | `RosterRow.print_serial_number` + `DerivedColumnId::PrintSerialNumber` | 每次生成名单时按当前筛选结果从 1 连续派生，**不持久化** |

**现有冻结契约是否支持该模型：支持，无需契约变更、无需破坏性迁移。** 依据（均从 `include/retiree_roster/schema_types.hpp` 直接读取）：

1. `person_code` 的能力元数据为 `source_importable=false, user_editable=false, system_managed=true`，`employee_no` 为 `true, true, false`。
2. `ImportFieldId` 与 `EditableFieldId` 都**不包含** `PersonId`／`PersonCode`，`is_valid_import_binding` 与 `is_valid_field_change` 也拒绝系统专管／Identifier 目标。因此**结构上不可能**出现“两个可写的固定编号来源”——这正是[标识符与编号口径](03_标识符与编号口径.md)当初提出撤销 `PersonCode` 所要防的情形，而当前契约已经用能力元数据把它排除了。
3. `RosterRow` 同时含 `person_id` 与 `print_serial_number`，`DerivedColumnId` 含 `PrintSerialNumber`，四者互不占用同一成员。

**若甲方未来确认“源工号与固定编号同义”**，采用**映射同值**而非删除字段：
- 服务在创建时按规则给 `person_code` 赋值（一次性快照等于当时的工号值）；不是把源列绑定到 `person_code`，也不新开可写来源。
- 创建后修改工号**不**改变固定编号（快照语义，满足 R05 的“固定编号稳定”）。
- 工号为空或重复时不能镜像，回退到系统分配的不复用编号；回退规则由甲方确认。
- 固定编号的格式（前缀、位数、校验位）由甲方给出；`Identifier` 为文本，格式变化不影响契约与数据库结构。

**待 R 认可的两处文字口径（文档层面，不是结构层面）**：
- [字段映射与数据保留策略](02_字段映射与数据保留策略.md)“系统分配 PersonId、PersonCode……不从源表映射”：登记口径理解为“不从源表**列映射**”，服务分配时取同值不违反该表述；若 R 认为该表述禁止取同值，则改为纯系统顺序号（同样零结构改动）。
- [标识符与编号口径](03_标识符与编号口径.md)“若确认等同，则以批准的局部变更撤销 PersonCode，不保留两个可写的固定编号来源”：该撤销建议针对的“两个可写来源”在当前契约下已不可能出现，本清单登记为**不再必要**；该文档的修订属 R／甲方决定，本轮不修改该文件。

## 4. DEFER_TO_D4

### A-D1-10 拼音排序键的自动生成方式（`AUTO_PINYIN_GENERATION_DEFERRED`）

- **领域结论**：`pinyin_sort_key` 在契约中已存在，为持久化、不可从源表导入、创建后允许人工编辑的文本字段。**D2 可按现状冻结该字段及其排序消费方式**；未定的是它如何被自动填充，而不是它是否存在。
- **因此不再作为 D2 blocker**：R04 的排序规则（键 → 姓名 → person_id）与键的生成方式解耦；即使键为空，排序仍由姓名与 `person_id` 决定，结果确定。
- **必须在 D4 前决定**：项目内置最小拼音表（含许可与来源登记）自动生成初值，还是首期只允许维护员手工录入。
- **现在不引入任何拼音库或第三方依赖。**
- **未来影响范围**：D4 规则／排序的初值质量与维护工作量；D5 导出顺序（消费同一快照与同一键）；若最终引入外部拼音表，C 轨需把它纳入构建与发行包并在[依赖台账](../dependencies/THIRD_PARTY.md)登记。
- **验收条件**：D4 必须证明在键为空、键相同、多音字人工改写三种情形下，UI／导出／打印顺序一致。
